# AGENTS.md

Single-page consultation scheduler (React 19 + Vite + TS + Tailwind v4, Supabase backend). No test framework and no GitHub Actions — Cloudflare Workers Builds runs `npm run build` on push, so a type error blocks the deploy. Docs are written in Malay (BM).

## Commands

- `npm run dev` — Vite dev server
- `npm run build` — `tsc -b && vite build` (this is the only typecheck; `noUnusedLocals`/`noUnusedParameters`/`verbatimModuleSyntax` are on, so unused code breaks the build)
- `npm run lint` — oxlint (config in `.oxlintrc.json`)
- `npm run preview` — serve `dist/`
- Verify changes with `npm run lint && npm run build` (lint first; there are no tests)
- Path alias `@` → `src/` (defined in both `vite.config.ts` and `tsconfig.app.json`)

## Deployment

- Hosting is **Cloudflare Workers**, not Pages: `wrangler.jsonc` declares service `consultschedule`, static assets from `./dist` with SPA fallback, custom domain `consultation.ajamlab.my`, `workers_dev: false`. `wrangler` is not a dependency — the build runner installs it and runs `npx wrangler deploy`.
- Deploy is automatic via **Workers Builds** (GitHub App "Cloudflare Workers and Pages"). Every push to `staging` **and** `main` starts a build (`npm run build` = `tsc -b && vite build`) and adds a "Workers Builds: consultschedule" check to the commit; a red check means nothing shipped (the first nine commits all failed this way).
- **The Production branch in Workers Builds is `main`** — changed in the dashboard on 5 Nov 2026 (it was `staging` until then). So **pushing `main` is the production release**; builds from `staging` and any other branch become preview versions and leave the custom domain untouched.
- Workflow: do the work on `staging`, push it there first if you want a preview, then fast-forward `main` and push it to release (`git checkout main && git merge staging && git push origin main && git checkout staging`). Never push half-finished work to `main`. To change which branch releases, use the dashboard (Workers & Pages → `consultschedule` → Settings → Build).
- **`.env.production` is committed but holds PLACEHOLDERS** (`PROJECT_REF_DIKELUARKAN`, `VITE_SUPABASE_ANON_KEY_DIKELUARKAN`), not real credentials. The real `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` must be set as **Build** variables in Cloudflare (Settings → Build → "Build variables and secrets" — *not* Settings → Variables & Secrets, which is runtime only and never reaches Vite). Env vars present at build time override `.env.production`. Saved build settings apply to the **next** build, so Retry the deployment or push a new commit after saving. Local dev reads `.env` (gitignored).
- **If the Build variables are missing, the site does NOT fall back to mock mode** — the placeholders are non-empty, so `isSupabaseConfigured` stays `true` and the deployed app calls `https://PROJECT_REF_DIKELUARKAN.supabase.co`, which does not exist: every booking/slot request fails and the CSP blocks it too. Symptom seen on 5 Nov 2026. To diagnose, download the live `assets/supabase-*.js` chunk and grep for `supabase.co` — a placeholder host there means the build never got the variables. The client now shows a warning banner (`src/components/ConfigWarning.tsx`, driven by `isPlaceholderSupabaseConfig` in `src/lib/supabase.ts`) when it detects these placeholders, so the failure is visible in the UI instead of silent.
- CSP lives in `config/headers.tmpl`, not `public/_headers`. The `emit-headers` plugin in `vite.config.ts` writes `dist/_headers` at build time and injects the Supabase origin from `VITE_SUPABASE_URL` into `connect-src` (plus the `wss:` form), so no project URL is hardcoded in the repo. Add a new external origin to the template, not to the generated file. A placeholder `VITE_SUPABASE_URL` therefore also produces a CSP that blocks the real Supabase host.
- Cloudflare never runs SQL — the deploy does not touch the database. Apply migrations in the Supabase SQL Editor.
- To redefine an RPC in a new migration, `DROP FUNCTION IF EXISTS` first with the exact argument signature, then `CREATE FUNCTION` — `CREATE OR REPLACE` cannot change a function's argument list (`0011` does this for `private.check_madam`/`public.madam_verify`). Match signature order of the latest definition.
- PIN Mod madam is `GANTI_PIN_INI` (bcrypt hash in `private.app_config`). Rate limits: madam 3 wrong tries / 5 min, student wrong ID 3 tries / 10 min. Client logic lives in `src/lib/rateLimit.ts`; server tables are `private.pin_attempts` and `private.booking_attempts`.

## Supabase / data layer

- Dual-mode: with `VITE_SUPABASE_URL` + `VITE_SUPABASE_ANON_KEY` (copy `.env.example` → `.env`) calls hit real Supabase RPCs; without them `src/lib/mock.ts` serves demo data with fake delays. `isSupabaseConfigured` in `src/lib/supabase.ts` is the gate — every hook in `src/lib/useSchedule.ts` branches on it. Add new data operations in BOTH branches. In mock mode, set `VITE_MOCK_MADAM_PIN` (e.g. `GANTI_PIN_INI`) in `.env` to unlock Mod madam locally (`MOCK_MADAM_PIN` in `useSchedule.ts`); never set it in production builds.
- All DB access goes through RPCs, not raw table writes (`book_slot`, `set_booking_status`, `add/remove_allowlist`, `add/remove_extra_class_block`). RPCs raise error codes as exception messages — match on `error.message` in `useSchedule.ts`: `NOT_ALLOWLISTED`, `INVALID_STUDENT_ID`, `WRONG_WEEK`, `INVALID_DAY`, `CLASS_TIME`, `SLOT_TAKEN`, `DAILY_LIMIT`, `OUT_OF_HOURS`, `INVALID_SLOT_LENGTH`, `RATE_LIMITED` (server lock), `UNAUTHORIZED` (madam-only RPCs), `ALREADY_APPROVED`, `NOT_YOUR_BOOKING`, `BOOKING_NOT_FOUND`. `book_slot` returns `null` instead of raising for a non-allowlisted student; `slots.ts` converts that to a `NOT_ALLOWLISTED` error.
- SQL lives in `supabase/migrations/`: run `0001` → `0022` in order, then `supabase/seed.sql` (Supabase SQL Editor or `supabase db push`). For a fresh DB, `supabase/setup_all.sql` is a one-paste concatenation of migrations + seed, but it is **gitignored and stale** (last regenerated 17 Oct 2026, stops at `0015`, so it is missing `0016`–`0022`) — regenerate it from the migration files before trusting it. Later migrations REDEFINE earlier functions — e.g. `0006` is the live `get_week_slots`, `0008` the live range-capable `get_week_slots`, `0010` the live `book_slot` (2-week prebooking window + race-safe daily limit), `0011` the security patch, `0012` removes student self-cancel, `0013` re-adds `student_name` (short code) to `get_week_slots`, `0014` enforced Monday online-only, `0015` is the live `book_slot` (weekend rollover window), `0016` re-adds `student_full_name` for approved blocks (hover full name), `0017` restores Monday online/f2f choice (`book_slot` without the Monday restriction), `0018` re-adds `cancel_booking_by_slot` (pending-only), `0019` adds the leaderboard (`get_leaderboard`, season config in `private.app_config`) and drops `clear_week_bookings`/`clear_week_extra_classes` (the "Reset week" button is gone), `0020` is the live `get_leaderboard` (scores a week as soon as the session ends + `first_slot_at` tie-break) and adds `private.kl_now()`, `0021` adds the Telegram notifier (`private.notify_telegram_booking` + trigger `trg_notify_telegram` on `public.bookings`), `0022` edits that message to "Withdrawn by student" when a pending booking is deleted (adds `private.telegram_sent`, `private.telegram_booking_text`, `private.telegram_harvest`, `private.notify_telegram_withdrawn` + trigger `trg_notify_telegram_withdrawn`, and redefines `notify_telegram_booking` to record the request id); don't re-run older definitions expecting them to stick.
- **Seed is split public/private** (since 5 Nov 2026). `supabase/seed.sql` is committed and holds the **class schedule only** — recurring `class_blocks` (`week_start = NULL`) for `owner = 'madam'` and `owner = 'student'`; it starts with `delete from public.class_blocks where week_start is null` so it is safe to re-run. The real student allowlist lives in `supabase/seed_private.sql`, which is **gitignored** (keep a copy in a password manager / private Drive, never in the repo): it adds `allowlist.full_name` (`if not exists`, already created by `0006`), deletes the `2099%` demo students left over from older seeds, and upserts the 7 real students (`student_id`, 3-letter `name` code, `full_name`) `on conflict (student_id) do update`. It also carries the commented-out `update private.app_config set value = extensions.crypt(...)` for the Madam PIN. On a fresh DB: migrations → `seed.sql` → `seed_private.sql`.
- Students **can** withdraw their own booking via `cancel_booking_by_slot` (by student ID) **only while it is `pending`** — once Madam approves it, only Madam can reject/clear it. `cancel_booking(uuid, text)` stays removed (no `booking_id` exposed); approve/reject still goes through `set_booking_status`.
- Security patch (`0011_security_patch.sql`): removes open read policies on `allowlist`/`bookings`/`class_blocks`, exposes class/week/booking data only through RPCs. New RPCs: `get_supervisees`, `get_class_blocks`, `get_active_booking_weeks`, `get_week_bookings`. It also sets the Mod madam PIN to `GANTI_PIN_INI` (hash bcrypt) and adds server-side rate limits: madam PIN 3 wrong tries / 5 min lock, student booking wrong ID 3 tries / 10 min lock (`private.pin_attempts`, `private.booking_attempts`, `private.client_bucket`). Client rate limits in `MadamGate`/`BookingDialog` match these values. To change the PIN: `update private.app_config set value = extensions.crypt('PIN_BAHARU', extensions.gen_salt('bf')) where key = 'madam_pin';`.
- **Telegram notifier (`0021_telegram_notify.sql`).** A trigger on `public.bookings` (`trg_notify_telegram`, `after insert or update of status`) calls `private.notify_telegram_booking()`, which POSTs to `api.telegram.org` through **pg_net** (`net.http_post`). It fires on exactly two events: a new `pending` booking and a transition to `approved` — not reject, not withdrawal. The message text is **English** (unlike the rest of the docs/UI) and carries the **short 3-letter code only**, never the full name. It is sent with `parse_mode: 'HTML'` — **not** MarkdownV2, which would demand escaping `-` `.` `(` `)` `!` `+` `=` `#` and more, while HTML needs only `&` `<` `>` (the student code is escaped for those three). Day *and month* names are built with a `CASE` rather than `to_char('Day'/'Month')` so they never depend on the server's `lc_time`; times go through a full `timestamp` (`week_start + (day_of_week - 1) + slot_start`) because `to_char` has no direct `time` overload, and AM/PM is printed once at the end when both ends share it, on both ends when the slot crosses noon. The only non-ASCII literal is the en dash, written as the 8-digit escape `E'\U00002013'` — use the 8-digit `\U` form, never 4-digit `\uXXXX`, which tooling tends to decode into a literal character before it reaches the file. This lives in the DB on purpose: the bot token is a full-control secret, every `VITE_*` is baked into the public bundle, and the CSP in `config/headers.tmpl` only allows `connect-src` to self + Supabase — so the client *cannot* be the sender. Nothing in `src/`, the CSP, or `wrangler.jsonc` is involved, and the trigger catches every path into the table (app, direct RPC, Mod madam). Config keys sit in `private.app_config`: `telegram_bot_token`, `telegram_chat_id` (group id, negative), `telegram_thread_id` (only for Topics groups), `telegram_enabled` (`'true'`/`'false'` kill switch). The migration inserts **empty placeholders** with `do nothing`; real values live in the gitignored `supabase/seed_private.sql` — never commit a token and never make it a `VITE_*`. Missing or disabled config makes the trigger return silently rather than error, and the whole function body is wrapped in `exception when others` that only `raise warning`s, because a failed notification must never fail a student's booking. pg_net is fire-and-forget (no retry); debug with `select id, status_code, content from net._http_response order by created desc limit 5;` — `401` = bad token, `400` = bad chat id, `403` = bot not in the group. One range booking is one `bookings` row, so it is one message, not one per 30 minutes.
- **Withdrawal edits the message in place (`0022_telegram_withdrawn.sql`).** When a student withdraws a `pending` booking (a DELETE via `cancel_booking_by_slot`), `trg_notify_telegram_withdrawn` rebuilds the same message with `Status: Withdrawn by student` and sends `editMessageText`. The message is deliberately **not** deleted, so Madam can still see that someone booked and then pulled out. This needs the original `message_id`, which is awkward because **pg_net is asynchronous**: `net.http_post` only queues the request and returns a request id, while Telegram's reply (carrying `message_id`) lands later in `net._http_response`. So the send records the request id in `private.telegram_sent`, and `private.telegram_harvest()` — called at the top of every notify/withdraw trigger — copies `message_id` across before pg_net purges the response (it keeps responses only a few hours). If the id still cannot be resolved, the withdraw path falls back to posting a separate `BOOKING WITHDRAWN` message rather than staying silent, because a group left showing "Awaiting Madam's Approval" for a booking that no longer exists can make Madam hold a slot for nobody. Both the send and the withdraw path build their text through the one shared `private.telegram_booking_text(...)`, so the two can never drift apart. The withdraw trigger is a **separate function** from the notify one: in a DELETE trigger only `old` exists, and mixing `new`/`old` in one body just invites null errors.
- **Promoting a group admin changes `telegram_chat_id`.** Telegram silently upgrades a basic group to a supergroup when you add an admin (seen 6 Nov 2026), and the chat id changes to a completely new `-100…` value — not a reformat of the old one. Notifications then fail with `400 Bad Request: group chat was upgraded to a supergroup chat`, and the new id arrives in that response's `parameters.migrate_to_chat_id`, readable via `select content from net._http_response where status_code = 400`. Update `telegram_chat_id` in `private.app_config` and it works again. Also beware pasting a token with the placeholder's angle brackets still attached (`'<token>'`) — that yields `404 Not Found`, not `401`; `select length(value) from private.app_config where key = 'telegram_bot_token'` should read 46, not 48.
- `get_week_slots` currently returns `student_name` (short 3-letter code) so the pending block can show the student code, plus `student_full_name` (full name) but only for `approved` slots so the hover tooltip reveals who was approved. `mode` and `booking_id` stay hidden.
- Business rules enforced server-side: max 1 active booking/day/student (`bookings_active_unique` partial index), booking window = current week + 2 weeks ahead, 30-min slots exactly, 08:00–18:00, slots overlap-free against `class_blocks`. Monday accepts both `online` and `inperson` modes like every other day (Monday online-only was reverted in `0017`).
- Range booking: students drag a multi-slot range (`useBookRange`). `book_slot` (redefined in `0008_range_booking.sql`, window widened in `0009_prebooking_window.sql`, weekend rollover in `0015_weekend_rollover.sql`) accepts any positive multiple of 30 min and stores it as ONE booking row; `get_week_slots` marks every covered 30-min slot. Max 1 active booking/day/student still applies.

## Conventions

- `week_start` is always the Monday of a week, anchored to `Asia/Kuala_Lumpur` on both server and client (`getCurrentWeekStart()` in `src/lib/slots.ts`). Booking is open for the current week plus 2 weeks ahead (`getBookableWeeks()` / `getMaxBookableWeekStart()`). Navigation goes back to Week 1 (`SEMESTER_WEEK1_START`): past weeks are view-only (`WeekTimeline` `readOnly`), so students and Madam can see earlier bookings. **Weekend rollover:** from Saturday 00:00 KL the *current* week becomes the next week (Sat/Sun add 7 days), so students land on the upcoming week while the finished week stays out of reach. Mirrored server-side in `0015_weekend_rollover.sql` — change both together. `day_of_week` is 1=Mon…5=Fri (`src/lib/types.ts`).
- i18n: inline `en`/`ms` dictionaries in `src/lib/i18n.ts` — every user-facing string needs both entries. App UI strings are BM/EN; code comments are often BM.
- Design tokens (colors, fonts, folder-card look) live in CSS custom properties in `src/index.css`; follow `DESIGN.md` and `PRD.md` for visual/business intent.
- Tailwind v4 is plugin-based (`@tailwindcss/vite`) — no `tailwind.config.js`; theme is configured in CSS.
- Leaderboard (`#rank`): plain hash routing in `App.tsx`. Ranking logic lives in `src/lib/leaderboard.ts` and is shared by mock and real mode. A week counts as soon as an `approved` booking's **session is over** — `slot_end` has passed in KL time, checked against `private.kl_now()` (`0020_live_scoring.sql`); it no longer waits for the week to end. There is no attendance marking; Madam only approves/rejects, and the count is computed live at query time, so a late approval fills its week in retroactively. `weeks[i]` is `null` when the week is undecided — a future week, or the current week with no finished session yet — which is what stops a student with a Wednesday slot from being shown as `missed` on Monday; `computeStats` stops at the first `null`. Ranking ties go weeks → longest streak → total sessions → **`first_slot_at`** (earliest counted consult slot wins; mirrors "whoever consulted first stays above"), with name A-Z only as the final determinism fallback. Keep `scoredWeeks()` as the denominator for levels/averages, not `completedWeeks()`, or `attended` can exceed the weeks counted. Client KL clock is `klNowStamp()` in `src/lib/slots.ts` — change it together with `private.kl_now()`. The page is a public view only (no "You" card, no student ID input); `get_leaderboard()` takes no arguments and never returns student IDs. Season start/length: `season_start`/`season_weeks` in `private.app_config` (mock uses `SEMESTER_WEEK1_START` + 12).
- Previewing in mock mode while `.env` points at real Supabase: run `npx vite --mode mock` (the gitignored `.env.mock.local` blanks the Supabase vars and sets `VITE_MOCK_MADAM_PIN=GANTI_PIN_INI`).
